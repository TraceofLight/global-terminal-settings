# Aqua Core CLI Split Design

## Goal

Move cross-platform daily CLI tooling from OS package baselines to aqua, while keeping OS-specific installers responsible for the minimum terminal bootstrap.

## Boundary

OS installers remain responsible for tools and wiring needed before aqua-managed tools can run:

- aqua
- NuShell
- WezTerm
- Git
- fonts
- managed configuration deployment
- Windows junctions and user environment repair
- macOS NuShell fallback symlink
- Linuxbrew bootstrap and WSL entrypoints

aqua becomes responsible for cross-platform CLI tools that do not need OS-specific install behavior:

- ripgrep
- fd
- fzf
- bat
- delta
- lazygit
- dust
- duf
- lsd
- fastfetch
- zoxide
- Starship
- carapace

Language runtimes and environment-specific SDKs remain user-managed. Java, Node, Python, Ruby, company SDKs, and project-local runtime policies belong in `autoload/user-overrides.nu`, a user's own aqua config, or a project config.

## Configuration Shape

The repository should add a managed aqua global configuration under `shared/aqua/aqua.yaml`. Installers should stage it to the user's config tree and make NuShell expose it through `AQUA_GLOBAL_CONFIG`.

NuShell should prepend aqua's root `bin` directory to `PATH` so aqua proxy links resolve before fallback OS paths. The root should follow aqua defaults unless `AQUA_ROOT_DIR` is already set:

- Windows: `%LOCALAPPDATA%\aquaproj-aqua`
- macOS/Linux: `${XDG_DATA_HOME:-$HOME/.local/share}/aquaproj-aqua`

The installer may run `aqua install --all` after staging the global config when `aqua` is available. Lazy install remains the safety net, so a transient install failure should not prevent shell startup.

## Package Manager Changes

The OS package baselines should replace `mise` with `aqua`.

After aqua is in place, daily CLI tools should be removed from the OS package baselines once their aqua package names are confirmed. Bootstrap-critical tools should stay in OS package baselines. `git` should remain OS-managed because aqua needs repository and network workflows to be available independently.

## NuShell Behavior

`shared/nushell/env.nu` should own aqua environment setup because PATH and environment variables are shell runtime concerns.

`shared/nushell/config.nu` should continue to source generated autoload files for tools that need shell integration, such as `starship`, `zoxide`, and `carapace`. Those integrations can still be generated by installers from the aqua-provided binaries after installation. Startup must tolerate missing generated files, matching the current behavior.

`autoload/user-overrides.nu` remains the extension point for Java and other environment-specific runtime configuration.

## Error Handling

If `aqua` is missing, NuShell should still start. The aqua PATH entry can be calculated from default paths without invoking `aqua`.

If the aqua global config is absent, `AQUA_GLOBAL_CONFIG` should not point to a missing file.

If `aqua install --all` fails, installers should warn and continue to deploy shell configuration. This keeps first login repairable and lets aqua lazy install retry later.

## Testing

Tests should cover the generated NuShell environment behavior without requiring network access:

- aqua root `bin` is added to `PATH` when the directory exists
- `AQUA_GLOBAL_CONFIG` is set only when the staged config exists
- existing optional autoload behavior still handles missing generated files

Installer tests should verify that managed aqua files are copied into the staging and live config locations.
